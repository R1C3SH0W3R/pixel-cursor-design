# 单文件通用指南：参考图生成像素动态光标

将本文件作为任务说明提供给能够看图的 AI Agent，同时提供参考图。无需技能安装、特定工具名或专用调用前缀。
执行者先检查本宿主的实际能力，再按下文完成制作；已有授权可用路径直接继续。宿主指令和权限始终优先。

本文件由技能的正式说明自动汇编，包含设计、动画、格式、检查和工具数据约定。完整技能包另附 Python 工具，单独提供本文件时不能假定这些脚本存在。
没有附带脚本但有可执行图像/二进制工具时，可按格式规范实现等效制作；缺少绘图或执行/文件交付能力时，需先说明具体缺口，不可宣称已生成。
默认交付 Windows 光标；执行 Agent 的系统可不同。不宣称所有 Agent 或所有产品版本都已经实测。

使用者可以说：请按照这份指南，把参考图制作成整套像素风动态光标，其余由你设计，给我预览和成品包。

## 参考图生成个性化像素光标

### 面向使用者的承诺

用户提供参考图（附件、可访问的文件或宿主支持的图片资源）即可开始。具备下述制作能力时完成并交付能使用的光标包，而不只是设计建议、提示词、示意图或待填写模板。用户不需要认识图中角色，也不需要懂光标技术。

技能执行者负责读取图片、设计动作、调用绘图能力、处理素材、编写所需渲染代码、填写内部配置、校准热点、验证和打包。**不要把这些工作转交用户，不让用户运行制作命令、填写 manifest、拆图、定位坐标或逐项指定 17 个动作。**

### 跨 Agent 接入

本文件是普通 Markdown 工作流；不要求特定 Agent、模型、工具名称、调用前缀、Shell 或技能目录。支持技能的宿主可加载 `SKILL.md`；不支持技能的宿主可直接读取 [通用入口](#portable-guide)，或读取同包的单文件 `PORTABLE_GUIDE.md`。`agents/openai.yaml` 仅是可忽略的特定宿主界面信息，不是运行依赖。

首次在新环境执行时，读 [能力适配](#guide-adapters)，用实际暴露的工具映射看图、绘图、像素处理、二进制导出和文件交付。优先复用宿主现成能力；Python 辅助脚本是可选实现，不是唯一执行路径。缺少某工具名不等于缺少对应能力；只能输出文字的 Agent 无法凭技能自行获得绘图和二进制文件能力。

保持宿主的指令优先级与权限边界。跨 Agent 指执行环境可适配，默认生成的光标仍用于 Windows；不要将其宣称为可直接应用于所有操作系统。

### 收到图片后的默认行为

- 新用户直接走 [从参考图到成品](#guide-process)。查看附件或用户明确指定文件夹中的图片；本机没有旧项目也可以完成。
- 用户未补充要求时，默认 Windows 10/11、完整 17 状态、细腻而可辨的像素风、参考图主体与配色、适合长期使用的轻微循环动作、32/48/64px、动态 ANI 加静态 CUR。默认值由助手采用，不要做成问卷；已有用户要求优先。
- 自动选取图中最显著主体，提取外形、色调、服装/材质和辨识物。人物、动物、物件、标志或抽象主题都可以使用；不要把所有主题改成猫耳女孩。多图通常用于身份、风格或姿势参考，由助手辨别。
- 简短说明采用的方向，然后继续完成；无需在原型、动作表、提示词或每种状态之间反复等待确认。仅在图片无法访问/看清、多个主体同等突出且选择会改变主题、明确需求冲突，或实际能力/权限缺失时询问必要信息。
- 如果图片已经在上下文中，不让用户重复上传。只有用户明确要求“先给方案/先看样稿”时，才以该阶段为终点。

### 执行路径

1. **检查可用能力。** 按 [能力适配](#guide-adapters) 选择当前环境支持的执行路径。已具备绘图能力就不询问密钥或模型；所需能力不依赖本地终端，也可以来自宿主提供的代码执行、插件或已授权服务。缺口用具体能力表述，不要求用户寻找一个本环境不存在的工具名。
2. **自动确定设计。** 读取 [设计与动作](#guide-design)，从图片选定风格基准，在项目内部记录配色、轮廓、像素密度与 17 个状态的姿态。每种状态与功能有真实互动；保留角色身份，区分“参考图姿势”与“所有状态必须同一姿势”。
3. **生成并制作动作。** 使用原图与已稳定的代表姿态保持身份一致；按状态生成所需不同姿势，准备眨眼、呼吸或合适的局部动作。角色、道具、功能层分开处理；固定指尖/笔尖/文本中心等指示点。详细步骤、提示词和无需用户介入的修正方式见 [完整流程](#guide-process)。
4. **生成全部文件。** 助手自行生成最终尺寸 RGBA 帧与内部清单。有 Python/Pillow 和脚本访问能力时用 `scripts/cursor_io.py build`；其他环境用已提供的等效编码工具或依照格式规范在可执行运行时实现。制作接口见 [内部工具](#guide-tools)。不要让用户填表。小范围修改保留已接受状态和其余文件。
5. **验证并交付。** 按 [Windows 文件与检查](#guide-format) 检查二进制、热点、全部帧边界和加载，另做视觉与语义检查。可用时以 `scripts/package_cursors.py` 生成总览/动画/热点图/说明与成品 ZIP；否则在宿主环境完成同等步骤。通过该宿主真实的附件、下载链接或文件产物机制交付，默认整套不能漏项。

### 完成标准

- 默认交付 17 个 ANI、17 个 CUR、一张标注状态的总览、可查看的动画预览、使用说明和一个下载 ZIP；用户明确只要静态或单个状态时按其范围交付。
- 主题从用户图片得来；风格统一，实际大小能辨认；身体与道具不被意外裁切，手臂/支撑/握持自然；各状态有明确功能和独立设计。
- 任何动作不移动点击指示点；热点逐尺寸校准、逐帧固定。最近的不透明像素可能属于角色，不可作为语义校准的替代。
- 明暗背景、实际尺寸、循环首尾和中间帧均查看。加载成功不代表系统实际播放已测；如不在 Windows，说明原生加载未测。
- 修复检查发现的问题并重新验证受影响范围，不把已知缺陷和“用户自行调整”的任务一起交付。能力不足导致未完成时准确说明，不声称已完成整套。
- 生成光标不自动修改系统指针。说明如何应用即可，系统安装仅在用户要求时进行。

### 向使用者展示什么

最终直接展示预览、成品 ZIP、简短的使用方式和真实检查结论。内部设计表、提示词、参数和源码留在项目中，不要求使用者阅读。支持用户继续用“更清晰”“换色”“抱着笔”这样的自然语言修改。

分发本技能时一并提供 [给使用者的说明](#portable-guide) 和整个技能文件夹。只有继续蕾姆方案或需要历史设计示例时才读 可选案例（完整包中的可选参考：references/rem-case.md）；案例不影响新用户默认设计。

## 按能力适配不同 Agent

### 入口和运行协议

本技能通过 Markdown 传递任务规则，不假设任何特定工具接口。先查看宿主当前提供的功能、工具说明与权限，再确定执行路径；不要发送本环境不存在的 `image_gen`、`exec` 或其他猜测调用。

| 宿主形态 | 如何加载 | 如何执行 |
|---|---|---|
| 支持技能文件夹 | 让宿主发现本包的 SKILL.md | 使用宿主实际提供的工具与路径 |
| 项目规则/工作区 Agent | 把整个包放入可读取的项目，用项目入口引用 SKILL.md | 遵循宿主规则文件机制；不自动覆盖现有规则 |
| 支持文件附件的聊天 Agent | 提供 PORTABLE_GUIDE.md 和参考图；能解压时也可提供整个 ZIP | 使用内置绘图、代码执行和附件导出 |
| 自定义工具调用框架 | 把技能正文/按需参考作为任务上下文，把真实工具按下表映射 | 由已有框架执行真实调用；能力名称不是新 API |
| 只有文字输出的模型 | 可读单文件指南并协助设计 | 缺乏绘图/执行/交付时不能独立完成成品，不能声称已生成 |

这些是接入方式，不是对每个具体产品/版本的实测认证。不要要求所有宿主使用相同安装目录、`$pixel-cursor-design` 前缀、YAML 界面文件或终端。

### 能力契约

以下名称用于内部规划，**不是需要原样调用的函数名**。

| 能力 | 必要输入与输出 | 可接受的实现 |
|---|---|---|
| 看图 | 接受参考图片，理解真实主体、风格和构图 | 模型原生视觉、查看图片工具或已有视觉服务 |
| 绘图/编辑 | 接受参考图和姿态约束，返回可提取的位图/图像资源 | 宿主内置绘图、已配置插件、本地图像模型或用户授权的图像服务 |
| 像素处理 | 实际读取像素/alpha、合成/缩放/减色、产生逐帧 RGBA 数据 | 代码解释器、Python/Pillow、JS 图像库、其他实际像素处理工具 |
| 编码与检查 | 能写入 CUR/ANI 二进制、重新解码核对、计算热点与帧时序 | 附带 Python 脚本、已有光标工具或依规范实现的其他运行时 |
| 文件交付 | 保存实际文件，提供用户可取得的 ZIP 和预览 | 宿主附件、artifact/download 工具、获授权文件系统 |
| Windows 原生检查（可选环境） | LoadImage/GetIconInfo 等实际加载与读回 | 当前 Windows 主机或已经授权的 Windows 执行服务 |

完整自动制作需要前五项，可以由多个已配置工具共同提供。没有命令行不等于不能生成文件：代码解释器和文件产物工具可能已足够。反之，仅能绘图但无法处理像素/编码的助手只能提供图片，不能谎称 PNG 已成为 ANI。

### 自动选择路线

1. **发现而非假设。** 查看工具目录、可执行运行时、工作区和文件交付机制。对于没有主动工具发现功能的宿主，使用它已声明的能力，不把某个工具名当必需条件。`scripts/probe_runtime.py` 只能检查它所在的 Python 环境，不能据其结果断言云端、浏览器或插件不可用。
2. **优先复用。** 使用已有、已授权且适合当前任务的绘图与执行能力。宿主自身的图像技能/说明存在时遵循它；不存在时不强制安装一个同名技能。不要为迁就附带脚本更换一个已可完成任务的运行时。
3. **选择编码路径。** 有 Python 3.10+、Pillow 9.1+ 和脚本访问时直接复用附带工具。没有这条路径但有等效工具时，按 [导出规范](#guide-format) 和 [数据约定](#guide-tools) 完成相同编码及检查。需要依赖时只在当前任务允许的环境中准备；不要更改用户全局设置来掩盖缺口。
4. **选择交付路径。** 本地 Agent 返回用户可访问的实际路径；云端 Agent 使用真实附件/下载机制，不把云端内部路径当成本机可打开的文件。图片预览通过当前宿主支持的方式展示，不硬编码某个平台的 URL 前缀。
5. **缺项才询问。** 能替代就继续；所有现有授权路径都无法满足某必需能力时，说明缺什么、目前已做到哪一步，以及一个具体可行的接入选择。不要静默切换到新的付费服务、代填凭据或要求用户提供技术设计参数。纯文字输出是能力限制，不是成功的降级成品。

宿主、模型和服务权限优先。本技能不授予新的外部上传/安装/收费权限，也不改变已有授权；用户已选用的图像服务按当前授权使用，不重复追问。密钥只通过宿主支持的本地/安全配置传递，不放进图片提示词、聊天、分发包或日志。

### 图片资源与文件路径

- 附件 ID、图像工具的资源 ID、URL、本地路径是不同对象。先依据实际接口取得可用的图像引用；不要把 `D:/...` 当作远程服务能访问的 URL，也不要凭空创造图片 ID。
- 远端返回图片时，用宿主允许的取回或文件产物方式保存像素；只显示预览但取不到源像素，仍不满足后续编码条件。不默认把私人参考图公开托管来换取一个 URL。
- 路径相对于技能实际位置、当前工作区或 manifest 所在目录解释。使用 Path/宿主路径 API 连接路径；Shell 调用根据实际环境正确引用，不混用 PowerShell、Bash 或 CMD 语法。
- 默认新建任务输出位置，参考图来源可为上传附件或用户选定文件夹。对于只有云端文件区的环境，也使用其可写空间，无需用户建立某个固定本机目录。

### 无 Python 的等效路线

不要求实现一个通用替代库；优先使用宿主现成工具。确实需要在 JS、其他语言或代码解释器中编码时，最低实现如下：

1. 得到每一尺寸、每一帧的 RGBA 像素数组，明确宽高、逐帧热点和时长；最终像素版采用一致的二值 alpha。
2. 按 [Windows 格式规范](#guide-format) 写小端 CUR 目录和 DIB/BGRA+AND，再写 ANI 的 RIFF/ACON 块。处理 256 尺寸的 0 哨兵、掩码行对齐和 RIFF 奇数字节补齐。
3. 从生成字节重新解析，检查尺寸、热点、alpha/mask、帧顺序和首帧一致；不只比较自家编码函数的输入对象。用独立解析或原生加载提高证据强度。
4. 用可用的图像和压缩库生成明暗背景总览、逐状态动画、热点图、状态对照和 ZIP。逐项保留 [内部工具](#guide-tools) 的交付要求。
5. 无 Windows 时标记原生加载未测；不是文件必然失败。只有代码文本、Base64 文本或示意图而没有可下载的实际文件，不算成品交付。

没有可用像素/编码库时，可以在具备执行能力的环境安装允许的依赖或使用已授权服务；不能只通过换扩展名补齐能力。

### 内部完成记录

每个任务记录实际采用的看图、绘图、处理、编码和交付方式，以及 `binary_checked`、`visual_reviewed`、`windows_native_checked`、`system_playback_checked` 的真实状态；未执行的检查标记未测。可记录为项目 JSON，但由助手填写，不给使用者加问卷。

跨 Agent 续作时一并保存实际参考资源、设计记录、源图、帧和现有产物。新 Agent 检查能否访问后再续作，不因日志写着“已完成”就推断文件仍存在。没有其他产品的实际运行证据时，只能声称提供兼容接入方式，不能声称“所有 Agent 实测通过”。

## 从参考图到成品：执行者流程

本流程的外部输入可以只有一张图片。以下分析、方案、提示词、坐标、脚本与 JSON 全部由助手完成，不向使用者索要技术资料。

### 读图与默认方案

1. 用宿主实际可用的视觉能力查看附件或用户指定图片，读真实画面，不凭文件名猜内容。把实际参考保存到任务的可写文件区；不能直接复制时保留宿主支持且可再次访问的资源引用，原文件不动。
2. 确认主体类别、轮廓、脸部/外壳结构、标志性颜色、配饰、材质、风格和希望保留的气质。未知角色也按可见特征设计，不以“不知道名字”为阻碍。截图里的按钮和聊天文字一般不是主题的一部分。
3. 多图时优先使用用户标注的角色图/风格图；未标注时，以主体清楚的一张锁定身份，其他图辅助姿势和像素风格。没有多个同等候选主体时自主决定，不逐图追问用途。
4. 以参考图为配色来源，用较深轮廓和明亮功能色增强可读性。不要默认蓝色、女仆服、猫耳或某个特定角色。人像可以转成保留身份特征的像素 Q 版；动物保持其身体结构，物件用翻页、摆动、开合等方式表达动作。
5. 没有用户约束时采用 64px 左右的可辨细节网格，导出 32/48/64px，12 帧左右、约两秒的温和循环。根据实际画面调整，而不要求用户选参数。高细节需求可增加原生 128px，并做加载验证；预览放大不等于细节增加。

起始进度说明可写：“我会沿用图片中的主角和配色，制作 17 种像素动态光标，并检查点击位置和完整显示。”随后立即继续，不把说明写成确认问题。

### 环境与绘图能力

- 先读 [能力适配](#guide-adapters)，发现当前实际可用的视觉、绘图、像素处理、二进制执行和文件交付能力。能用已配置功能就直接用，不要求用户配置 API 或选择模型。
- 宿主有图像工作流、插件使用说明或 SDK 封装时遵循它，使用真实接口；没有某个特定名称的技能或工具，不等于缺少绘图能力，不把安装另一个产品的技能作为前提。
- 用户明确选择了自己的 API/模型路径时，使用相应获授权接口和实际支持的封装。参考图不能携带上一位使用者的接口授权，不复制作者的密钥、端点或本机配置。
- 没有图像生成能力时，说明无法自动绘制新的姿势；已有工具允许的图像流程或用户明确选择的服务可用后再继续。不要用一张贴图换 17 个角标、程序画的占位人物、复制旧作者角色等方式冒充完成。
- 附带工具使用 Python/Pillow；文件制作也可由代码解释器、JS、现有光标工具或已授权的等效服务完成。助手按真实能力选择执行路线并准备允许的依赖；没有 Python 时先找替代，不让用户更换 Agent 或运行制作命令。
- 此处“只需图片”描述绘图与文件能力就绪时的输入体验，不表示技能本身提供云端服务、额度或离线图像模型。

### 助手内部的设计记录

在新项目内维护一个简短设计记录，方便续作，不向用户发填写问卷：

```text
reference_files: 实际参考路径
subject: 可见身份与轮廓
keep: 必须保持的颜色、服饰/形体、配饰、风格特征
palette_and_grid: 实际色板、像素网格、轮廓粗细
target: Windows / 尺寸 / 轻微动态
states: 每个文件 ID 的姿势、道具接触、图层顺序、热点语义、动画
accepted_baseline: 选定的代表姿态及输出路径
```

17 个状态与文件 ID 见 [设计与动作](#guide-design)。为每个状态设计有区别的行为，不让人头贴纸占据准星中心；不把忙、后台工作做成相同外观。文本的倚靠/趴睡、忙的休息、笔的握持都是可选方向，须适配图中主体。例如猫用爪与身体接触道具，不凭空增加人手；机械主题用构件转动而非眨眼。

### 建立代表姿态并扩展

1. 从提供的图片提取身份和风格，先生成一幅适合小尺寸的透明角色素材；对用户已有像素图可保留其原始造型。采用 [提示词骨架](#guide-design)，按实际主体填好内容。
2. 查看实际返回图片、透明背景、面部特征和四肢，制作一个实际显示大小的代表状态。助手自己对照参考检查，通常无需等待用户审核。
3. 把参考图与代表姿态作为后续绘图参考，为每个状态生成所需的新动作。准确说明“角色身份保持不变，仅改姿态与表情”；复杂握持应把角色、手臂、道具关系一起生成，功能指示点仍由后续精确布局控制。
4. 默认逐状态可控地制作与检查。如果使用格子图，明确每格区域、足够间距并逐格检查；拆图由助手做，不要求用户切图。不要要求模型在一张图中同时精确输出所有 17 状态的多帧小像素及热点。
5. 图像工具不严格遵守尺寸、alpha 或构图时，以实际产物为准处理；若结构错误，针对这个姿势修正。单个姿势在两次有明确针对性的重试仍无改善时，改用更清楚、较简单但符合功能的姿态，或保留可用版本并准确报告未解决项；不无限循环收费请求，也不偷偷换服务。

有真实的原生图像能力时要实际调用并保存产物，不能只留下生成提示词后结束。仅做方案或流程测试时，不把未运行的绘图和动画制作描述成实测完成。

### 制作像素与动作

- 去除实际背景，裁紧源素材的可见轮廓，保持手脚和道具完整。高分辨率图单次缩到目标角色区域，映射至共享色板且不抖动；对已有像素图避免平滑。每个目标尺寸都检视眼睛、手与道具尖端。
- 助手在项目中实现本主题的渲染函数与需要的图层分离。功能图形可用确定性的绘制代码，复杂角色姿态来自实际素材；通用工具不负责从坐标模板凭空绘制新人物。
- 用不同表情/姿态或局部变形制作动作。眨眼需要闭眼形状，呼吸固定底线，笔尖和指尖固定。不能把整体平移、亮度跳动或只有沙漏动当作所有状态的角色动作。
- 缺少动作图层时，根据实际素材补出局部状态或生成所需关键帧。不要每帧独立随机重画角色，避免身份漂移、颜色闪烁和衣服跳变。
- 保存每个状态在每个尺寸的完整 RGBA 帧。根据该尺寸的功能层确定热点；遇到尖端在缩小后消失时修正像素，不把最近的角色像素当尖端。
- 输出供编码器使用的内部 manifest；每种尺寸下帧数相同，热点固定。参数由助手计算并写入，无需用户提供。

建议项目布局：`references/` 保存用户参考，`source/` 保存生成素材与提示词，`frames/` 保存最终帧，`work/` 保存内部设计与清单，`files/` 保存光标，`delivery/` 保存干净交付包。目录名可以适应已有项目，成品包不带凭据或整个工作区。

### 编码、检查和交付

1. 按 [内部工具](#guide-tools) 导出文件。默认整套必须有全部 17 种动态与静态文件；局部修改按用户范围生成，不意外覆盖其他角色。
2. 先独立解码导出图与目标帧比较；检查语义热点、角色结构、动作首尾、所有帧边界和配色。对要求“底部齐平”等情况做图层级计算。不能只凭 GIF 或格式检查判断通过。
3. Python 路线且脚本实际可访问时调用 `package_cursors.py`：它执行成品格式/覆盖/边距检查，Windows 上默认进行原生加载，再生成总览、每个状态的 GIF、热点图、状态对照和 ZIP。只有单文件指南或采用其他运行时时，按格式规范在实际执行环境中实现同等编码、解码与打包，不假定该脚本已经存在。检查漏项或错误后修复再打包。
4. 查看打包后的明暗背景、实际尺寸和动画，确认缩略图没把角色糊成块、GIF 无残影。如果某一步没有实测，报告它，不能沿用旧项目检查结果。
5. 用宿主支持的预览方式显示总览和一个代表动画，通过真实文件交付机制提供 ZIP，并简述状态与应用方法。云端内部路径不能假冒用户可访问的链接。不要以“还需要你填写配置/手动导出”为完成答复。

### 修订现有方案

“像素高一点”要结合图片理解为细节或颗粒要求；“抱着笔”处理接触与遮挡，不只移动道具；“热点偏了”核对实际文件与应用状态。保留已接受的其他文件并比对哈希。对于明确要求全套重设风格，再扩大修改范围。

<a id="guide-design"></a>

## 设计、像素与动态

### 先锁定可读性

记录三种不同尺度：源图分辨率、实际绘制的逻辑像素网格、系统显示尺寸。把 64px 图最近邻放到 128px 只会扩大颗粒，不会增加人物细节；1024px 原图直接压到 32px 也未必可读。

以参考图而非固定数字决定密度。64px 可作为许多角色光标的起点；需要细腻表情时可制作原生 128px 版本，同时为 32/48/64px 简化细节。不要把原本可辨认的脸压到十几个像素宽，再用锐化补救。放大系统指针能增加显示面积，但嵌入高分辨率条目本身不能强迫 Windows 使用它。

两类输入采用不同处理：

- 已经画好的像素图：保留原有格点与色板，整数倍放大使用最近邻；48px 之类非整数比例需要检查一像素线条，必要时单独绘制。
- 高分辨率生成图：去掉背景和光晕，按真实轮廓裁边；一次缩到目标角色区域，再映射到整套共享色板，关闭抖动，手动修正眼睛、手指等关键像素。需要高细节版本时从源图重新制作。

统一轮廓、亮暗层级、肤色和功能色。整套可使用几十种颜色，但不要强制所有风格固定颜色数量。像素轮廓通常采用二值 alpha；先清除带背景色的半透明边缘，再阈值化，透明像素 RGB 清零。保留已经匹配色板的像素，避免重复减色改变被接受的图。

不同角色可有不同姿势，但应属于同一套画法。若用户明确要求某个状态更细腻，记录这个局部例外，不擅自重画全套。

### 角色与功能布局

以下表格用于覆盖和识别，不强制使用表中的道具。`Windows 值名`只帮助区分系统角色，不是修改注册表的指令。

| 状态 / 文件 ID | Windows 值名 | 识别与热点 | 可用的个性化设计方向 |
|---|---|---|---|
| 正常选择 `normal` | Arrow | 箭尖或明确指向点 | 角色在箭头侧后方陪伴 |
| 帮助选择 `help` | Help | 主指示箭尖 | 歪头、看问号或翻书 |
| 在后台工作 `background` | AppStarting | 保持可用箭尖 | 侧边等待符号，角色忙碌 |
| 忙 `busy` | Wait | 稳定的合理中心 | 抱沙漏、小憩；不必额外加箭头 |
| 精确选择 `precise` | Crosshair | 准星交点 | 角色置于侧下方，保留瞄准中心 |
| 文本选择 `text` | IBeam | 工字杠中部 | 倚靠或趴在杠旁，留出文字区域 |
| 笔 `pen` | NWPen | 笔尖 | 双手抱笔或骑笔，遵循指定方向 |
| 不可用 `unavailable` | No | 稳定的合理中心 | 拒绝手势、双臂交叉 |
| 垂直调整大小 `vresize` | SizeNS | 双向轴中心 | 沿上下轴推拉或伸展 |
| 水平调整大小 `hresize` | SizeWE | 双向轴中心 | 左右拉伸、展开双臂 |
| 对角线调整大小 1 `diag1` | SizeNWSE | 左上—右下轴中心 | 沿对应斜轴抱住箭杆 |
| 对角线调整大小 2 `diag2` | SizeNESW | 右上—左下轴中心 | 反向斜轴动作；不要导出成同一方向 |
| 移动 `move` | SizeAll | 四向交点 | 角色推四向柄，四个方向完整 |
| 备用选择 `alternate` | UpArrow | 上箭尖或约定指向点 | 向上伸手或托起箭头 |
| 链接选择 `link` | Hand | 食指尖 | 完整连接手臂的举手动作 |
| 位置选择 `location` | Pin | 实际图形的指示点 | 独立地图针用针尖；组合手形用指尖 |
| 个人选择 `person` | Person | 主手形指尖 | 把旁侧小半身像换成主题角色 |

“完整”是预定构图内的身体与道具都可见。个人选择可以有意使用半身像，不能因此机械要求全身。按所有帧轮廓的并集留边；最终像素边界检查不能发现源图本来就缺失的手脚，必须看图。

图层关系可采用：后臂 → 道具 → 前臂/手掌 → 局部衣袖。握持处需要手指、手腕、前臂连续，掌面贴着道具，遮挡关系一致。禁止用一团白色补丁代表手或用道具挡住脸来掩盖问题。

### 图像生成提示词骨架

先提供最接近的已接受参考。生成任务只承担角色绘画与复杂接触；精确 I-beam、准星和热点通常适合后续确定性绘制。

```text
用途：透明背景的小尺寸个性化鼠标光标角色素材。
主题和身份特征：{角色、发型、服饰、配色、辨识物}。
风格基准：{参考图；像素颗粒、头身比例、轮廓、色板}。
这个状态：{功能}；动作：{身体、表情、手臂与道具的关系}。
构图：{人物/道具区域、朝向、功能符号需要的空白}。
接触与遮挡：{哪只手在前、身体如何支撑、笔尖等朝向}。
完整呈现：保留所需四肢、耳朵和道具端点，外围留透明余量。
不加文字、边框、展示卡、装饰性光晕或未要求的功能符号。
```

实际检查返回尺寸、alpha 和背景，不假定模型完全遵循尺寸或透明参数。凭据仅在本地读取并传入调用进程；不要输出到提示词、日志、技能或成品中。如果生成结果结构有误，修正针对性的姿态描述；布局和热点问题应在布局层解决，避免无目的重复生成。

### 动作与接触约束

- 眨眼包含睁眼停留、闭眼短暂停留和恢复；不要每帧随机改变眼形。
- 呼吸改变躯干或头部局部轮廓，保持支撑点；睡眠状态一直闭眼，不夹杂睁眼帧。
- 举手可动耳朵和衣摆，指尖不抖；抱笔可动身体，笔尖固定；文本杠和准星本体保持静止。
- 伸懒腰需为手脚预留整段动作空间，不裁剪极值帧；若动作牵涉指示手，则改动另一只手或身体。
- 循环首尾姿态衔接，色板一致，避免道具跳位和随机纹理闪烁。帧数和时长由动作决定；例如 12 帧、每帧 10 jiffies 是约两秒循环的参考，不是统一规定。

当要求趴睡角色与文本杠底部齐平时，使用共享基线 B。对裁紧的角色层以 `y = B - opaque_height` 放置，杠底的独占坐标也为 B。呼吸改变高度后重新从 B 向上定位；对每个尺寸和帧比较 alpha 包围盒的底坐标，而不是画布高度。

### 视觉验收

查看实际 1 倍尺寸、整数倍最近邻放大、深浅背景和动画。逐个回答：功能可辨吗？角色身份还清楚吗？手臂接得上吗？道具被合理握住吗？功能中心被遮挡吗？最外帧完整吗？各状态有独立动作吗？

热点图需标出像素中心 `(x + 0.5, y + 0.5)`。它用于发现视觉偏差，不能仅因热点落在任何不透明像素上就判定正确。

## Windows 导出、热点和故障定位

### 可靠的编码路径

优先使用现有且验证过的导出器。有 Python/Pillow 时可用本技能的 `scripts/cursor_io.py`（见 [工具接口](#guide-tools)）。它采用经典 32 位 DIB，提供静态 CUR 和等时长、顺序播放 ANI 的保守子集。以下二进制规则与编程语言、Agent 品牌无关；在其他可执行运行时可实现等效编码，但必须实际解码检查产物。

CUR：

- ICONDIR 为 `reserved=0, type=2, count=N`，每项 16 字节；宽高字段 0 表示 256，两个 WORD 是热点 x/y，不能误写成 ICO 的色面/位深。
- DIB 为 40 字节 BITMAPINFOHEADER，宽 W，高为 `2*H`；先底部向上的 BGRA XOR 像素，再底部向上的 1 位 AND mask。
- AND 每行按 32 位对齐，行字节数 `((W+31)//32)*4`；透明像素置 1。二值 alpha 与 mask 一致，透明 RGB 清零。

ANI：

- 使用 `RIFF` / `ACON`，`anih` 为 36 字节；`LIST` 的类型为 `fram`，每个 `icon` 块嵌入一个完整 CUR。
- `AF_ICON=1` 表示嵌入图标/光标帧；它不是“开启动画”的按钮。每个 RIFF 块长度不含填充，奇数字节补零；RIFF 总长度为文件长度减 8。
- 等速顺序播放可省略 `rate`、`seq `。`JifRate` 的单位是 1/60 秒，不能直接填写毫秒。
- `rate` 和 `seq ` 是合法块；不能把过去的加载失败一概归因于它们。若使用序列，需正确设置 `AF_SEQUENCE=2`，验证每个索引和步数；本技能导出器不产生这类扩展，但验证器支持解析顺序与时长。

PNG 内嵌 CUR 并不等于所有 Windows ANI 加载路径都接受。若面向经典系统光标，DIB 更容易保持兼容；不要通过改扩展名转换文件。

### 无附带脚本时的完整最小编码约定

以下仅定义本技能采用的 32 位、二值 alpha、DIB CUR 和等时长顺序 ANI 子集，足够在 JS 或代码解释器中独立实现。所有数值按**小端序**写入；`U8/U16/U32` 是无符号 1/2/4 字节，`I32` 是有符号 4 字节。尺寸为 1..256，热点使用最终像素坐标，不能使用浮点数。

CUR 文件以 6 字节目录头开始：`U16(0), U16(2), U16(N)`。之后连续写 N 个 16 字节条目，再写各个图像 payload。条目的偏移以该条目起点计：

| 字节偏移 | 类型 | 字段与取值 |
|---|---|---|
| 0 | U8 | 宽；256 写 0 |
| 1 | U8 | 高；256 写 0 |
| 2 | U8 | 颜色数量，32 位图写 0 |
| 3 | U8 | 保留，写 0 |
| 4 | U16 | 热点 x |
| 6 | U16 | 热点 y |
| 8 | U32 | payload 字节长度 |
| 12 | U32 | payload 相对整个 CUR 文件起点的字节偏移 |

第一个 payload 偏移为 `6 + 16*N`，随后逐项累加前一 payload 长度，CUR 条目之间不额外补齐。

每个 payload 是以下 40 字节 DIB 头、XOR 像素、AND 掩码的连接。DIB 头偏移从 payload 起点计：

| 偏移 | 类型 | 字段 | 本子集取值 |
|---|---|---|---|
| 0 | U32 | biSize | 40 |
| 4 | I32 | biWidth | W |
| 8 | I32 | biHeight | 2*H |
| 12 | U16 | biPlanes | 1 |
| 14 | U16 | biBitCount | 32 |
| 16 | U32 | biCompression | 0（BI_RGB） |
| 20 | U32 | biSizeImage | W*H*4（XOR 字节长度） |
| 24 | I32 | biXPelsPerMeter | 0 |
| 28 | I32 | biYPelsPerMeter | 0 |
| 32 | U32 | biClrUsed | 0 |
| 36 | U32 | biClrImportant | 0 |

XOR 从图像最下行向上写，每行从左到右，像素次序 BGRA。32 位每行已按 DWORD 对齐，长度正好 `W*H*4`。透明像素写全零；不透明 alpha 为 255。AND 也从下行向上写，每行 `((W+31)//32)*4` 字节，先清零；透明像素对应字节的 `0x80 >> (x%8)` 位设为 1。不透明位为 0，右侧行填充位保持 0。payload 总长为 `40 + W*H*4 + and_stride*H`。

ANI 的最小构造如下，其中 `chunk(tag,data) = ASCII4(tag) + U32(data.length) + data + (data.length 为奇数时补 1 字节零)`：

```text
frame_list = ASCII4("fram") + 拼接每帧的 chunk("icon", 完整CUR字节)
body = chunk("anih", anih_header) + chunk("LIST", frame_list)
ani = ASCII4("RIFF") + U32(body.length + 4) + ASCII4("ACON") + body
```

`anih_header` 恰为 36 字节，按下表依次写 9 个 U32。此最小路线不写 `rate` 和 `seq `。

| 偏移 | 字段 | 等速顺序播放取值 |
|---|---|---|
| 0 | cbSizeOf | 36 |
| 4 | cFrames | F，实际 CUR 帧数量 |
| 8 | cSteps | F |
| 12 | cx | 0，让每帧的 CUR 条目提供尺寸 |
| 16 | cy | 0 |
| 20 | cBitCount | 32 |
| 24 | cPlanes | 1 |
| 28 | JifRate | 正整数，单位 1/60 秒 |
| 32 | flags | 1，即 AF_ICON |

每帧都放相同尺寸集合，每个尺寸的热点固定。静态 CUR 使用动画首个播放帧；动画至少有两个视觉不同的帧。数据写完后重新读取所有长度、偏移、像素与热点，不要只确认字节数组非空。

下面是**格式自检样本，不是用户光标设计**。一个 1×1 不透明红像素、热点 (0,0) 的 CUR 应有 70 字节，完整十六进制如下；去掉换行后解码：

```text
00000200010001010000000000003000000016000000280000000100000002000000
010020000000000004000000000000000000000000000000000000000000ffff00000000
```

此文件的图像 payload 偏移 22、长度 48，唯一 RGBA 像素应解码为 (255,0,0,255)。把同尺寸蓝像素作为第二帧，各 10 jiffies，按上述 ANI 公式应得到 224 字节；其前 56 字节应为：

```text
52494646d800000041434f4e616e69682400000024000000020000000200000000000000
0000000020000000010000000a00000001000000
```

这些字节用于检查端序与长度；不能用这个单像素样本证明正常尺寸、17 个状态、角色动画或系统播放正确。对正式产物仍执行后面的分层验证。

### 尺寸与热点

32/48/64px 是可选起点。需要高分辨率时可加 128px，所有尺寸都要从合适源图或逻辑图生成，最终核对细线、轮廓与热点。

一次历史案例中，12 帧 ANI 嵌入 `[32,48,64,96,128]` 无法加载，改为 `[32,48,64,128]` 后通过。此现象只证明那组产物的差异，**不是 Windows 最多支持四个尺寸的规则**。遇到类似失败应构建最小样本、逐个增加尺寸和帧数，记录目标系统的实测结果。

热点位于最终像素坐标：箭头尖、食指尖、笔尖、工字杠中部、准星交点或双向轴中心。空心准星的热点可以透明；忙/不可用的稳定中心也可能透明。透明度不是所有状态通用的正确性判据。

每个尺寸独立定义正确热点，所有帧复用。若缩放使尖端消失，优先补回关键像素；必须吸附时，只在已知功能层的小范围内找候选，不能吸到附近人物。若指尖会动，应修动作，不能通过每帧改变热点补偿。

### 分层验证

1. **输入与布局**：查看源图是否已被裁切，帧画布、动作范围、图层接触与语义指示点是否正确。
2. **成品二进制**：独立读取导出文件，检查目录、偏移、DIB、mask、RIFF 长度、帧/步数和时序；核对所有尺寸热点稳定以及 CUR 是否等于 ANI 首个播放帧。
3. **针对性像素检查**：与目标渲染逐像素比较，检查共享色板、二值 alpha、边界和关键接触点。像素块放大时的网格一致性可用缩回逻辑尺寸再最近邻放大验证，但只适用于该状态既定网格。
4. **Windows 加载**：以 `LoadImageW(..., IMAGE_CURSOR=2, W, H, LR_LOADFROMFILE=0x10)` 加载，`GetIconInfo` 读回热点、`GetObjectW` 核对位图尺寸。释放 `GetIconInfo` 返回的两个 bitmap 与非共享 cursor handle。不修改注册表或系统方案也能完成这一步。
5. **视觉和交互**：预览循环，检查首尾和中间帧。应用后在文本、链接和调整大小场景检查实际体验；只有实际进行了这一层，才能声称系统中已验证播放和交互。未经要求，不自动替用户应用方案。

非 Windows 环境仍可解析文件，但应注明原生加载未测。脚本通过不能证明角色萌度、结构自然、系统播放正常或应用选择了正确状态。

### “改 ANI 没反应”的排查顺序

- 确认生成的是新的文件，内容/哈希发生变化；查看用户当前选用的路径与对应角色，是否仍选中了静态 CUR 或旧副本。
- 检查 ANI 是否含多个不同的可见帧、合理的时长和正确循环；预览动了不代表 ANI 编码正确。
- 原生加载失败时，从一个尺寸、两帧的 DIB ANI 开始，逐步恢复尺寸、帧数和高级块，找到具体触发条件。保留通过和失败样本，避免盲目删块或修改系统设置。
- 原生加载成功而界面仍旧时，让用户在鼠标“指针”设置选择对应状态的 `.ani` 并应用；必要时先切到默认方案应用再重新选择，以刷新缓存。
- 某些应用使用自己的光标；先在使用系统光标的场景区分应用行为和文件问题。

发现导出错误可以在原范围内修复；新调用付费生成服务、安装或写入系统配置仍受当前用户授权与执行权限约束。不要把缓存推测当作诊断结论。

### 可交付证据

保留每个状态的尺寸、帧数、时长、热点、SHA256 和检查报告，以及带标签总览、局部动画、热点标注图。报告应区分解码检查、原生加载和实际应用验证。GIF 只用于预览；它的调色板与透明机制可能引入残影，预览可使用不透明背景和明确的 disposal，不让预览问题污染真正的 RGBA 帧。

## 内部制作、检查与自动交付工具

本页供执行技能的助手使用，不是使用者需要操作的说明。使用者可以只上传参考图；助手负责产生素材、最终帧、热点与下述清单并运行所有命令，不让用户填写 JSON 或运行 Python。

本页描述附带 Python 工具的实现路径，其他 Agent 可以采用 [能力适配中的等效路线](#guide-adapters)。不要求终端：能在代码解释器导入模块也可调用相同函数。未得到脚本文件时，不假定代码存在；使用完整技能包，或依据格式规范在现有运行时实现。

`scripts/cursor_io.py` 使用 Python 3.10+ 和 Pillow 9.1+，不读取密钥、不联网、不安装系统光标。用已确认的 Python 解释器运行 `scripts/probe_runtime.py` 可检查这条本地路线；探测器不判断宿主的看图/绘图工具，也不需要联网。源图设计与像素处理先完成，再交给编码器。已有可靠导出器可继续使用。

### 输入约定

使用透明 RGBA PNG，每一帧已处于最终画布上；宽高和 manifest 的尺寸一致。像素 alpha 仅 0/255；工具不会擅自缩图、改色、阈值化或吸附热点。透明像素的 RGB 会归零。

manifest 的所有相对图片路径相对于 manifest 文件所在目录，状态名作为输出文件名。一个状态所有尺寸具有相同帧数，热点为该尺寸的一组固定整数坐标。默认 jiffies 为 10，可在状态级覆盖。单帧只输出 CUR，多帧输出 CUR 和 ANI；多帧内容必须有差异。

```json
{
  "version": 1,
  "jiffies": 10,
  "states": [
    {
      "name": "text",
      "sizes": {
        "32": {"hotspot": [7, 16], "frames": ["frames/text-32-00.png", "frames/text-32-01.png"]},
        "64": {"hotspot": [14, 32], "frames": ["frames/text-64-00.png", "frames/text-64-01.png"]}
      }
    }
  ]
}
```

这里的坐标仅是格式示例，实际需按图像的功能指示点确定。工具支持 1..256 的方形尺寸；库函数 `encode_cur` 也接受矩形图。不要默认导出所有可能尺寸。

### 命令

下列 `SKILL_DIR`、`PROJECT` 是由助手替换的路径标记，不是预设环境变量。`python` 指已确认可用的解释器；不同宿主可能使用 `python3`、完整解释器路径或直接执行 Python 代码，不能假定某命令名必然存在。

```text
python "SKILL_DIR/scripts/cursor_io.py" build "PROJECT/manifest.json" --out "PROJECT/cursors-new"
python "SKILL_DIR/scripts/cursor_io.py" validate "PROJECT/cursors-new" --margin 1 --native --report "PROJECT/validation.json"
```

默认不覆盖已存在的同名输出。备份后，已授权的重复构建可加 `--overwrite`，不用因此重新询问用户。工具不会清除旧目录中的其他文件；从动态改为静态时，优先导出到新目录，避免遗留旧 ANI 造成误选。

`validate` 可接受目录或多个文件，目录只扫描直接子文件。`--native` 仅 Windows 可用，会真实加载文件、读回热点与尺寸，但不应用到系统；其他平台省略它并如实说明未做原生检查。`--margin 1` 要求全部帧距边缘至少一像素；这是适用于本类完整角色图的检查参数，不是 CUR 格式的规定。

报告包含 SHA256、尺寸、热点、帧/步数、时长、不同帧数量、错误和原生加载计数。工具独立解析 DIB 与 RIFF，核对 alpha/mask、所有帧热点不动、边距、静态文件与 ANI 首个播放帧一致。`validate` 成功返回 0，任何失败返回 1。

解析器面向本技能的二值透明、32 位 DIB 子集，不支持 PNG payload 或其他合法编码；遇到“超出支持范围”不应宣称文件必然损坏。输入文件过大或来源不明时先查看体积与结构，不无限制重复尝试。

### 需要另做的检查

- 功能语义：脚本不知道笔尖、指尖、文本杠在哪，不能自动证明热点正确。
- 共享色板与轮廓风格：将解码图与目标图/基准对照；没有强制固定色数。
- 特殊布局：如角色与杠底对齐，需要在渲染层保存角色和功能层分别检查。
- 真实播放：原生加载不是系统动画演示，不能据此称已安装或已测试所有应用。
- 美术质量：实际大小、手臂接触、完整人物、首尾衔接和主题辨识仍需看图。

Python 中也可使用 `encode_cur([(image, (x, y)), ...])`、`encode_ani([cur_frame, ...], jiffies)`、`parse_cur(data)`、`parse_ani(data)`。后两者返回解码帧与时序，可接入已有针对性检查，避免复制此工具或把项目资产放入技能目录。

### 解析和无损提取既有动画

`parse_cur(data)` 返回 `{(width, height): ((hotspot_x, hotspot_y), PIL_RGBA_image)}`。`parse_ani(data)` 返回 `(frames, sequence, rates)`：frames 是 CUR 解码字典列表，sequence 是每个播放步骤引用的帧索引，rates 是每个播放步骤的时长，单位 1/60 秒。重复帧用于停留，不能去重后改变动作速度。

例如，助手可按 `for step, index in enumerate(sequence)` 遍历，用 `frames[index][(64,64)][1].save(...)` 保存逐步 PNG，并从对应 tuple 读取热点。这些坐标是输入成品的数据，不能照搬给新主题。重建等时长 manifest 时保留重复步骤；变时长可转为公约数步长的重复帧，或沿用支持 rate/seq 的现有导出器，避免未经验证的超大帧数。

### 自动成品包

`scripts/package_cursors.py` 同样只依赖 Python/Pillow，与 `cursor_io.py` 同目录。它接收已经导出的光标文件，负责最终检查、预览和交付；不会从参考图自动绘画，因此助手必须先完成 [参考图流程](#guide-process)。

```text
python "SKILL_DIR/scripts/package_cursors.py" "PROJECT/files" --out "PROJECT/delivery" --slug "my-pixel-cursors" --title "个性化像素光标"
```

默认强制完整 17 个状态的 CUR 和具有可见变化的 ANI，检查边距至少一像素。Windows 上自动做原生加载，其他平台明确标记未测。然后输出：

- `my-pixel-cursors.zip`：直接给使用者的成品。
- 同名目录里的 `files/`：34 个光标文件。
- `preview/overview-light.png`、`overview-dark.png`：深浅背景、1 倍大小和整数倍放大总览。
- `preview/<state>.gif`、`hotspots.png`：逐状态动画与热点图。
- `使用说明.md`、`cursor-map.json`、`validation.json`：应用方法、17 状态对照和真实检查记录。

包内路径相对化，只复制指定成品，不夹带整个工作区、原用户图片、密钥、生成脚本和本机路径。使用已有文件夹/包名时会停止以避免覆盖；修订可换输出目录或版本名。

只有用户明确要求局部修改时添加 `--states text pen` 之类的范围；明确只要静态时添加 `--static`。`--no-native` 会跳过并如实标记原生检查，不得用它掩盖原生加载失败。可选 `--margin` 适配有意贴边的设计，不应拿它掩盖不完整构图。

打包器生成的是技术检查和预览，不会替助手判断人物身份、手臂自然度、语义热点和动作流畅性；助手仍需打开产物查看并修复实际问题。
